# Windows MP4 recording

Use `powershell.exe -NoProfile -ExecutionPolicy Bypass -File '{{HELPER}}' video`. It runs the maintained bundled `scripts/video.mjs` with the bundled application runtime and FFmpeg/ffprobe. No installer, model calls or second Codex session.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File '{{HELPER}}' video doctor
powershell.exe -NoProfile -ExecutionPolicy Bypass -File '{{HELPER}}' video windows
powershell.exe -NoProfile -ExecutionPolicy Bypass -File '{{HELPER}}' video capture --hwnd 123456 --crop 0,110,1920,828 --seconds 5 --fps 30 --width 1920 --require-motion true --out "C:\Projects\MyGame\Evidence\my-task\after.mp4"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File '{{HELPER}}' video video --input "C:\Projects\MyGame\Evidence\my-task\source.mp4" --seconds 5 --fps 30 --width 1920 --require-motion true --out "C:\Projects\MyGame\Evidence\my-task\after.mp4"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File '{{HELPER}}' video inspect --input "C:\Projects\MyGame\Evidence\my-task\after.mp4"
```

1. Before editing, identify the intended Unity instance, scene and Game View display. Note the original gameplay camera and the routing you may need to restore, such as active state, tag, camera controller or stack, and camera-bound UI. Enter **Play Mode**, then poll Unity Editor state until it reports playing and unpaused with compilation and the Play Mode transition complete. If the user already has a running session, use it only when you can capture and restore the camera without disrupting it.
2. In Play Mode, create a temporary recording camera and keep its object ID for cleanup. Match the intended projection, clipping, layers and render settings, then apply the planned framing. Route the Game View display through this camera using the actual runtime camera controller, render stack or camera bindings. If the project resolves its camera by `MainCamera`, transfer the tag temporarily. Preserve required overlays and camera-bound UI, and keep a single active AudioListener. Keep capture objects and assignments in the running session.
3. Open **Game View** and verify that the expected camera drives its rendered output. After the switch, wait for multiple fresh frames, confirm the expected framing and effects, and check that loading or initialization has finished and frame delivery has settled. Poll for readiness within a bounded window. If the Editor reloads, reconnect to the same instance and recheck. Use both the confirmed Play Mode state and fresh Game View frames before starting the recorder.
4. Enumerate windows, select the Unity HWND and measure the client-relative crop of the rendered Game View. Capture `before.mp4` before editing. Save the camera transform, projection and render setup, display, view resolution or aspect ratio, crop, runtime starting point, action, input timing and duration. After verification, repeat the complete setup and readiness checks for `after.mp4`.
5. After each attempt, including a failed or cancelled recording, restore the original gameplay camera, routing, tags and any UI or camera settings you changed. Remove the temporary camera by object ID and verify that it is gone and the original camera renders again. Restore the initial Editor view and exit only a Play Mode session you started. Exit the baseline session before editing.
6. If the runtime camera or Play Mode readiness cannot be confirmed, or a side cannot be captured, record the specific missing-video reason for that side. Keep the comparison in Play Mode for both sides. The baseline must come from the original, unmodified state.

The HWND and crop above are placeholders. Exclude toolbars, editor overlays and surrounding panels from the crop. Restore any temporary view changes and preserve the user's camera, selection and dirty state. Never record unrelated desktop content or resize/upscale a small source to label it HD.

`--width` is an output maximum, not a resize target. The helper uses the smaller of the source width and this maximum, preserves the source aspect ratio, and never enlarges a source. A true1920×1080 window client captured with `--width 1920` remains1920×1080. A1280×720 client stays1280×720. Smaller windows, crops, or sources must be reported at the actual size; do not infer1080p from the monitor resolution. Capture receipts record both the actual output `width`/`height` and the window `captureSource.clientWidth`/`clientHeight` plus any crop. Verify these values with ffprobe before publishing.

Defaults:5seconds,30fps, up to1920px wide without upscaling. Combined caps:15seconds,30fps,1920 maximum edge,2,073,600canvaspixels,128MiB per MP4. H.264 AVC/yuv420p, CRF15 with the ultrafast preset, faststart. CRF15 with the ultrafast preset keeps the fastest encoder preset while applying a moderate quality increase over the previous CRF17 baseline. It preserves the existing frame-rate, pixel-format, duration and thread bounds. One decoder/filter/encoder thread at BelowNormal priority; output-local scratch, bounded heap, one recording/test job at a time. Source and existing output files are preserved.

Before publication, use the video helper to inspect each local MP4 and review decoded frames across the clip. Check for repeated or frozen frames during expected movement. If the recording adds stutter beyond what you observe in Game View, recheck the capture and retry. Inspect the original full-resolution PNG files separately.

Publish paired videos with `evidence.beforeVideo` and `evidence.afterVideo`, or use `videoViews` for named angles. Confirm the report ID and managed artifact IDs from the MCP response or helper receipt. For replacements, use the same report ID and confirm the artifact for the requested role or view through MCP. Leave the app window and its current page untouched.
