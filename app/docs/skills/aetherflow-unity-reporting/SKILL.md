# Unity work → AetherFlow

AetherFlow is the user's local desktop production/planning application. This Skill is installed globally in Codex by AetherFlow's explicit setup button; it is independent of any Unity project or character workspace. Keep AetherFlow open while using its MCP tools. Its **Unity Activity** section stores reports independently of character production. Its MCP server starts with the app. Use this skill throughout a Unity work item, not only at the end when a baseline has already been lost.

## Global helper

The MCP server is named `aetherflow` in Codex. Use its exposed tool names (for example `project_get_context` and `unity_report_publish`); a CLI may show a server prefix. If tools are not loaded yet, restart/reconnect Codex after setup, without closing the user’s active work. Do not edit global authentication, model/provider settings, or AGENTS.md. The local PowerShell helper below uses the installed application runtime and reads authentication locally; never print or copy its token.

FFmpeg and ffprobe are included with AetherFlow. The installed helper selects their exact paths from `installation.json`; a separate user installation and PATH changes are unnecessary. Run the video helper's `doctor` before capture; if the application was moved or tools are missing, repeat setup or repair the installation. Scratch defaults to `.aetherflow-recording-temp` beside the output, on any drive. All shown evidence paths and HWNDs are examples; use the actual project and window.

## Start

1. Read project-local instructions and use the installed Unity MCP skill for Editor operations. Discover/select the intended Unity instance; never address the Unity HTTP bridge directly. Preserve the user's current scene, dirty state, selection, and Play mode. Do not start another Editor merely to record evidence.
2. Query AetherFlow context through `project_get_context` if available, otherwise run:
   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File '{{HELPER}}' report context
   ```
   Use the intended AetherFlow project returned by context, its `locale`/`settings.locale` (`en` or `ru`), and canonical existing tasks. Pass that project's actual `id` explicitly as `projectId` in the report; an older profile can have no saved active-project selection. If multiple projects make the target ambiguous, resolve the intended project before publication. Write report title, summary, checks, and missing-evidence explanations in that language. Keep project paths, identifiers, code and commands exact. Do not infer the report language from a terminal language.
3. Create a small evidence directory for this work item, within the task's approved project evidence directory. Save the actual **before PNG and before MP4 before editing**. Record a short reproducible action or preview and note its camera, crop, duration and action sequence so the after recording can match it. A screenshot does not substitute for the before video. Request **1920×1080 PNG** explicitly from Unity MCP (the tool default may be only640×360), then inspect the actual decoded dimensions and visual detail. If still unclear, inspect render scale, dynamic-resolution factors and mip limits read-only; dimensions alone can hide internal upscaling. Do not change the user's quality settings automatically. Match view, camera and framing for the after capture. Preserve original image bytes; never publish a thumbnail or upscale a small image as HD. If an old baseline is low-resolution, retain it and label any new capture honestly; a later recapture cannot recover the original baseline's detail.

## Work and evidence

- Implement and validate the requested change through the relevant Unity/project workflow. AetherFlow reporting supplements it; it does not replace compilation, affected tests, visual inspection or user review.
- Capture the **after** image of the same subject at1920×1080 PNG. Record the **after MP4**, matching each before MP4's camera angle, framing, action, crop, duration and settings; normally5seconds,30fps, native viewport detail up to1920px wide. A camera angle is one distinct view: if you report Front, Side or Detail, capture a real before/after pair for each named angle. Capture all intended before clips before editing and their matching after clips after verification. Save and publish these as ordered `videoViews`, with a stable slug ID and localized label per view; never split a single recording into fake camera steps. Use H.264/yuv420p, high quality and faststart. Do not use GIF as the primary result. A real1920×828 viewport is preferable to upscaling it to1920×1080; report its true dimensions. Prefer the relevant viewport over an entire Editor with tiny panels. Do not turn a slideshow into purported gameplay.
- Use `powershell.exe -NoProfile -ExecutionPolicy Bypass -File '{{HELPER}}' video` and the bundled FFmpeg tools. Enumerate windows and select the exact Unity HWND, then capture a native client-relative viewport crop. Do not record the desktop or unrelated applications by default. Verify that minimized/occluded/black capture did not occur. When real capture is unavailable, record an honest missing-video reason rather than manufacturing footage.
- Run one capture/encode/test job at a time. Keep the utility's bounds (15 seconds, 30 fps, 1920 px maximum), single-thread encoding and low process priority. Use a short clip and sequential disk-backed passes; do not buffer an entire high-resolution recording in RAM. Store scratch beside the output on the project drive. Do not turn off the user's applications or change Windows settings.
- Use `--require-motion true`, inspect the decoded dimensions/frame rate/duration and visible subject motion, then check the **actual MP4 inside AetherFlow**. Different hashes, a populated video element, or an encoded30fps flag alone do not prove smooth playback. Measure media-time progression and presented/decoded/dropped frames (for example requestVideoFrameCallback/getVideoPlaybackQuality), and check that frames do not stall for seconds. Check play/pause, seek, fullscreen and pause on inactive/minimized views. A small relevant animation may need a tighter crop; noise, a cursor or timestamps do not establish the requested behavior.
- A Scene view may repaint while the intended shader or simulation is frozen in edit mode. Check its actual driver, including renderer MaterialPropertyBlock overrides; a zero value in the shared material alone proves nothing about rendering time. For an existing ExecuteAlways preview, a bounded Scene-view repaint and `EditorApplication.QueuePlayerLoopUpdate()` can run the component's genuine Editor preview. Verify the subject itself moves; label it **Editor preview**, preserve view state, and avoid claiming Play-mode/gameplay verification. Do not change materials/time uniforms or start the user's game merely to manufacture a clip. If only a camera orbit was captured for an integration test, label it as a **scene inspection** and restore the exact camera/view state.
- If baseline capture was missed, the work is nonvisual, or capture is unavailable, report the exact limitation in the corresponding view's `missingEvidence.beforeVideo` or `missingEvidence.afterVideo`; each view side requires exactly one real file or a specific missing reason, and each view must contain at least one actual clip. Images remain separate optional `before`/`after` roles. Localize all labels and reasons using AetherFlow's language. For genuinely single-view work, use the legacy paired roles or one explicit view; do not invent additional angles. Historical single-result `video` is compatibility-only and can appear solely on the After side. Never copy it into Before or relabel a later recording as the baseline. Never recreate a fake baseline, claim a static file is motion, invent passing checks, or mark a result human-approved. For a recording-only integration check say explicitly that no Unity feature was changed. Existing GIF reports remain readable for history; new reports use video.

## Publish

Use one `unity_report_publish` call or the helper below, with a stable per-work-item idempotency key. Keep the summary to 2–4 useful sentences; list actual checks separately. Evidence is copied into AetherFlow's managed storage; do not edit the user's originals. Link existing `taskIds` rather than creating duplicate planner tasks. Never mark a task complete just because a report was published.

Create a UTF-8 JSON manifest using the exact [manifest contract](references/report-manifest.md), then:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File '{{HELPER}}' report publish --manifest "C:\Projects\MyGame\Evidence\my-task\report.json"
```

The helper uses the app's authenticated local MCP; it works even when the current Codex session has no AetherFlow MCP tools configured. Do not read or print `mcp-token`, copy it into prompts, or change global provider/auth settings. It does not call Unity's internal bridge.

If AetherFlow is closed/unreachable, preserve the manifest and evidence, report **pending publication**, and retry the same command/key after it opens. Do not claim publication based on a local manifest. If an older running app lacks the publish tool, explain that AetherFlow needs to be reopened normally; do not restart the user's running app without coordination.

To improve an existing report, use `unity_report_replace_evidence` or `powershell.exe -NoProfile -ExecutionPolicy Bypass -File '{{HELPER}}' report replace --manifest ...` with the existing report ID, its current revision, role (`beforeVideo`, `afterVideo`, `before`, `after`; `video` and `gif` are legacy), file, reason and stable key. For an explicit camera view, also pass its `viewId` slug with `beforeVideo` or `afterVideo`. Refresh the revision between separate role replacements. Preserve tasks and previous managed evidence/history. Never overwrite stored bytes or duplicate the report to replace poor media. **Verify the actual existing report now points to the new files**: an isolated QA pass or files left in scratch are not delivery. See the [replacement manifest](references/report-manifest.md).

## Finish criteria

- Relevant Unity checks completed, with actual outcomes and any outstanding limits stated.
- Before/after PNGs and **two MP4 videos (before and after)** are real captures, or each missing role has an honest reason. The before video was recorded before implementation, not reconstructed afterward. Check actual original-resolution images in AetherFlow, including100% mode.
- Every intended camera angle has a real matched before/after pair or an honest side-specific missing reason. Verify each MP4 for codec/dimensions/timing, visible motion and continuous actual AetherFlow playback. Switch camera-view steps and confirm only the selected pair is loaded; check shared pause/seek/speed/fullscreen, both available media times advancing together, the shorter common duration, and inactive-stop behavior. No claim of30fps based only on metadata.
- MCP publish returned success with a report ID and managed evidence artifact IDs, or an explicit pending-publication path is given.
- Final user response briefly says what changed, what was verified and where to find the AetherFlow report. Never claim an Editor test when Unity was unavailable.

Read [Windows MP4 commands](references/windows-video.md) for normal recording. [GIF commands](references/windows-gif.md) are for legacy compatibility only. This package contains no model calls, paid service setup or installer.
