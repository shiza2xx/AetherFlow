# Unity work → AetherFlow

AetherFlow is the user's local desktop production/planning application. This Skill is installed globally in Codex by AetherFlow's explicit setup button; it is independent of any Unity project or character workspace. Keep AetherFlow open while using its MCP tools. Its **Unity Activity** section stores reports independently of character production. Its MCP server starts with the app. Use this skill throughout a Unity work item, not only at the end when a baseline has already been lost.

## Global helper

The MCP server is named `aetherflow` in Codex. Use its exposed tool names (for example `project_get_context` and `unity_report_publish`); a CLI may show a server prefix. If tools are not loaded yet, restart/reconnect Codex after setup, without closing the user’s active work. Do not edit global authentication, model/provider settings, or AGENTS.md. The local PowerShell helper below uses the installed application runtime and reads authentication locally; never print or copy its token.

FFmpeg and ffprobe are included with AetherFlow. The installed helper selects their exact paths from `installation.json`; a separate user installation and PATH changes are unnecessary. Run the video helper's `doctor` before capture; if the application was moved or tools are missing, repeat setup or repair the installation. Scratch defaults to `.aetherflow-recording-temp` beside the output, on any drive. All shown evidence paths and HWNDs are examples; use the actual project and window.

## Start

1. Read project-local instructions and use the installed Unity MCP skill for Editor operations. Discover/select the intended Unity instance; never address the Unity HTTP bridge directly. Preserve the user's current scene, dirty state, selection, and any running Play Mode session. Do not start another Editor merely to record evidence.
2. Query AetherFlow context through `project_get_context` if available, otherwise run:
   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File '{{HELPER}}' report context
   ```
   Use the intended AetherFlow project returned by context, its `locale`/`settings.locale` (`en` or `ru`), and canonical existing tasks. Pass that project's actual `id` explicitly as `projectId` in the report; an older profile can have no saved active-project selection. If multiple projects make the target ambiguous, resolve the intended project before publication. Write report title, summary, checks, and missing-evidence explanations in that language. Keep project paths, identifiers, code and commands exact. Do not infer the report language from a terminal language.
3. Create a small evidence directory for this work item, within the task's approved project evidence directory. Save the actual **before PNG and before MP4 before editing**. Record the before MP4 from **Game View in Play Mode**. Choose a reproducible runtime starting point and action. Note the scene, runtime camera, Game View resolution or aspect ratio, crop, duration and input timing for the after capture. A screenshot does not substitute for the before video. Request **1920×1080 PNG** explicitly from Unity MCP (the tool default may be only640×360), then inspect the actual decoded dimensions and visual detail. If still unclear, inspect render scale, dynamic-resolution factors and mip limits read-only; dimensions alone can hide internal upscaling. Do not change the user's quality settings automatically. Match view, camera and framing for the after capture. Preserve original image bytes; never publish a thumbnail or upscale a small image as HD. If an old baseline is low-resolution, retain it and label any new capture honestly; a later recapture cannot recover the original baseline's detail.

## Work and evidence

- Implement and validate the requested change through the relevant Unity/project workflow. AetherFlow reporting supplements it; it does not replace compilation, affected tests, visual inspection or user review.
- Capture the **after** image of the same subject at1920×1080 PNG. Record the **after MP4 from Game View in Play Mode**, matching each before MP4's runtime starting point, camera angle, framing, action, crop, duration and settings; normally5seconds,30fps, native viewport detail up to1920px wide. A camera angle is one distinct view: if you report Front, Side or Detail, capture a real before/after pair for each named angle. Capture all intended before clips before editing and their matching after clips after verification. Save and publish these as ordered `videoViews`, with a stable slug ID and localized label per view; never split a single recording into fake camera steps. Use the bundled H.264/yuv420p encoder at CRF15 with its ultrafast preset and faststart. Do not use GIF as the primary result. A real1920×828 viewport is preferable to upscaling it to1920×1080; report its true dimensions. Prefer the relevant viewport over an entire Editor with tiny panels. Do not turn a slideshow into purported gameplay.
- Treat `--width` as a maximum output width, never a request to enlarge a smaller source. At a genuine1920×1080 display and capture window, keep a1920×1080 client image at1920×1080. Keep a 1280×720 viewport at1280×720; do not upscale it. When the window or crop is smaller, record and report the actual output size from the helper receipt and ffprobe. Do not claim 1080p based on the display alone.
- Use `powershell.exe -NoProfile -ExecutionPolicy Bypass -File '{{HELPER}}' video` and the bundled FFmpeg tools. Enumerate windows and select the exact Unity HWND, then capture only the rendered Game View image using a native client-relative crop. Do not record the desktop or unrelated applications by default. Verify that minimized/occluded/black capture did not occur. When real capture is unavailable, record an honest missing-video reason rather than manufacturing footage.
- Run one capture/encode/test job at a time. Keep the utility's bounds (15 seconds, 30 fps, 1920 px maximum), single-thread encoding and low process priority. Use a short clip and sequential disk-backed passes; do not buffer an entire high-resolution recording in RAM. Store scratch beside the output on the project drive. Do not turn off the user's applications or change Windows settings.
- Before publication, inspect each local MP4 with the video helper and review decoded frames across the clip. Check dimensions, frame rate, duration, visible subject motion and repeated or frozen frames during expected movement. An encoded 30 fps flag or a changed frame hash alone cannot establish smooth capture. Use a tighter crop if the relevant animation is small.
- For each clip, create a **temporary recording camera in Play Mode** and route the active Game View display to it as the gameplay camera through the project's camera system. Record the original camera state first and reuse the same recording camera setup for the matched clip. Follow the [Windows MP4 camera workflow](references/windows-video.md).
- Before starting capture, confirm through Unity that Play Mode is active and unpaused. After assigning the camera, check that multiple fresh Game View frames show the intended framing and that startup frame pacing has settled. A successful Play command or a fixed delay alone cannot confirm readiness.
- After each capture attempt, restore the original gameplay camera and bindings, remove the temporary recording camera, and verify cleanup. If you started Play Mode for the baseline, exit it before editing. Restore the original Editor view and mode after recording. If camera routing or Game View readiness cannot be verified, record the specific missing-video reason for that side.
- If baseline capture was missed, the work is nonvisual, or capture is unavailable, report the exact limitation in the corresponding view's `missingEvidence.beforeVideo` or `missingEvidence.afterVideo`; each view side requires exactly one real file or a specific missing reason, and each view must contain at least one actual clip. Images remain separate optional `before`/`after` roles. Localize all labels and reasons using AetherFlow's language. For genuinely single-view work, use the legacy paired roles or one explicit view; do not invent additional angles. Historical single-result `video` is compatibility-only and can appear solely on the After side. Never copy it into Before or relabel a later recording as the baseline. Never recreate a fake baseline, claim a static file is motion, invent passing checks, or mark a result human-approved. For a recording-only integration check say explicitly that no Unity feature was changed. Existing GIF reports remain readable for history; new reports use video.

## Publish

Use one `unity_report_publish` call or the helper below, with a stable per-work-item idempotency key. Keep the summary to 2–4 useful sentences; list actual checks separately. Evidence is copied into AetherFlow's managed storage; do not edit the user's originals. Link existing `taskIds` rather than creating duplicate planner tasks. Never mark a task complete just because a report was published.

Confirm publication from the successful MCP response with `data.report.id` and the managed artifact IDs for the submitted evidence, or from the helper receipt with `reportId` and `managedArtifacts`. A report without attachments can have an empty artifact list. If the response is inconclusive, use `unity_report_list` for read-only confirmation or retry the same manifest and idempotency key. Leave the app window and its current page untouched. The MCP confirmation completes publication verification.

Create a UTF-8 JSON manifest using the exact [manifest contract](references/report-manifest.md), then:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File '{{HELPER}}' report publish --manifest "C:\Projects\MyGame\Evidence\my-task\report.json"
```

The helper uses the app's authenticated local MCP; it works even when the current Codex session has no AetherFlow MCP tools configured. Do not read or print `mcp-token`, copy it into prompts, or change global provider/auth settings. It does not call Unity's internal bridge.

If AetherFlow is closed/unreachable, preserve the manifest and evidence, report **pending publication**, and retry the same command/key after it opens. Do not claim publication based on a local manifest. If an older running app lacks the publish tool, explain that AetherFlow needs to be reopened normally; do not restart the user's running app without coordination.

To improve an existing report, use `unity_report_replace_evidence` or `powershell.exe -NoProfile -ExecutionPolicy Bypass -File '{{HELPER}}' report replace --manifest ...` with the existing report ID, its current revision, role (`beforeVideo`, `afterVideo`, `before`, `after`; `video` and `gif` are legacy), file, reason and stable key. For an explicit camera view, also pass its `viewId` slug with `beforeVideo` or `afterVideo`. Refresh the revision between separate role replacements. Preserve tasks and previous managed evidence/history. Never overwrite stored bytes or duplicate the report to replace poor media. Confirm the replacement through MCP by matching the report ID and returned artifact ID to the requested role and view. Use `unity_report_list` if you need to confirm the currently linked artifact or refresh the revision. See the [replacement manifest](references/report-manifest.md).

## Finish criteria

- Relevant Unity checks completed, with actual outcomes and any outstanding limits stated.
- Before/after PNGs and **two MP4 videos (before and after)** are real captures, or each missing role has an honest reason. The before video was recorded before implementation, not reconstructed afterward. Inspect original-resolution PNGs locally before publication.
- Every intended camera angle has a matched pair recorded from Game View in Play Mode or a specific missing reason for the affected side. Verify each local MP4 for codec, dimensions, timing and visible motion before publication. Confirm the original gameplay camera was restored and the temporary recording camera was removed after capture.
- The MCP response or helper receipt confirms the report ID and any submitted evidence IDs. If confirmation is unavailable, give the pending-publication path.
- Final user response briefly says what changed, what was verified and where to find the AetherFlow report. Never claim an Editor test when Unity was unavailable.

Read [Windows MP4 commands](references/windows-video.md) for normal recording. [GIF commands](references/windows-gif.md) are for legacy compatibility only. This package contains no model calls, paid service setup or installer.
