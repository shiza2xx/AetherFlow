# AetherFlow model workbench

Use for inspection, additions and corrections in Atelier, including work outside a production stage. Read the common pipeline and relevant repair Skill. Keep the embedded terminal's bound character session/cwd.

1. Read `ui_get_context` and `model_workbench_get_context`. Distinguish inspected step, persisted production step and independent working version. Resolve exact character/model/hash, rig status and canonical tasks.
2. Open the character/workbench with `model_workbench_open` or `ui_navigate`; wait for real acknowledgement. Navigation never accepts a result or finishes a stage. Read actual tool schemas.
3. `artifactId`/`sourceId` identifies the editable managed source and its hash/revision. When `ui_get_context` returns `viewerArtifactId`, that is the exact model currently displayed; use it for existing viewer hierarchy, camera, animation and capture tools. A generated GLB may be the displayed derivative of an editable `.blend`. Trust viewer state only while the renderer heartbeat is current; never substitute the display ID for the correction source ID. Compare source artwork at useful full-body and detail distances. Interactive 1024 px textures do not imply low-resolution stored files.
4. Classify cause: assignment/import, shader/material, image/UV, geometry, placement, rig/weights or animation. Use `aetherflow-mesh-repair`, `aetherflow-texture-repair` or `aetherflow-character-assembly-rig` accordingly.
5. `model_workbench_begin_correction` requires current source hash/revision, purpose, goal and explicit target object names. Include intended new mesh names for geometry additions. Use returned checkpointed working/dependency paths; never edit CAS files or originals.
6. Open the staged copy with `model_workbench_open_blender` or use trusted single-thread background scripts. Preserve declared unaffected objects. Do not run heavy checks simultaneously or equate process exit0 with successful output.
7. Save a new file, then `model_workbench_submit_correction` runs the trusted independent audit and registers pending model/report. Caller-authored JSON cannot certify success. Pin the submitted candidate ID and SHA-256 for review. Read the submit audit fields actually returned: `sourceBytesPreserved`, `candidateBytesVerified`, `reopenedVerified`, `protectedObjectsPreserved`, `declaredTargetPropertiesPreserved`, `rigAndActionsPreserved`, `changedObjects`, `geometryChangedObjects`, `requiresNewSurfaceBaseline`, `boundRigObjects`, source/candidate hashes, purpose, target objects, limitations and Blender version. These generic workbench fields do not certify exact UV correspondence, protected texture pixels or visual quality; use operation-specific compositor/application receipts for those claims. Reopen wherever a distinct required validation phase needs it (for example, compositor self-check, trusted submit audit, or visual review); reuse receipts for the same unchanged hash within a phase. As a finite default, inspect the source-matched whole model and the affected region at matched views. Add a capture only for a distinct affected region, view, or unresolved visual question; do not force a fixed screenshot count when the repair scope needs more evidence. Reuse the submit audit for its reported preservation checks and exact-hash compositor/application receipts for UV correspondence, mask conservation and protected pixels. If the candidate hash changes, the renderer reports stale state, or a required check fails, stop and rerun only the affected validation for the new candidate. Sequence navigation, readiness, camera change acknowledgement and capture. After opening a version, resolve its actual displayed artifact ID/hash from the acknowledged UI/viewer context; never guess a derivative ID or reuse the prior source preview ID. Do not issue open, camera change and capture concurrently. If adoption changes the active version during review, reread its identity and avoid reopening an obsolete source merely to finish reporting. If `viewer_capture` returns queued/running with a `commandId`, call `viewer_inspect` with both the same displayed artifact ID and that `commandId`. Reuse a late completed capture only when the response includes the matching command ID, source artifact ID/hash, capture artifact ID/hash, MIME and hash-verified `bytesBase64`; otherwise report the receipt fields available and do not enqueue a duplicate blindly. If it is still pending, wait through the current 30-second viewer lease and inspect that command once more; if it remains pending, report its ID/status and stop rather than polling or queuing a duplicate. After the pinned candidate has a successful audit and the needed reopened visual evidence, return the pending candidate for human adoption and stop capturing and polling. Handle a later adoption decision when it is provided; do not wait for it through repeated captures or polls. Do not repeat completed captures or full scene audits for an unchanged candidate. Inspection alone should not create a changed candidate.
8. Report changes, actual evidence, protected data, limitations and next action briefly in the app language. Human workbench adoption and production Accept/Continue remain distinct. Changed topology/UV/placement requires new applicable baselines and dependent checks before production reuse. Retain failed candidates and update the same linked task.

Weights require an actual bound rig. After geometry changes, remap required attributes/keys/skin/supports; old vertex numbers cannot establish new correspondence. Common `workbench_audit.py` protects declared objects/purpose, not unproved within-object masks, anatomy, all collisions or Unity appearance. Use stronger operation-specific receipts where available.
