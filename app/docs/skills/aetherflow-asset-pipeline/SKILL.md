# AetherFlow asset production

Use this skill when the current AetherFlow production owner is an asset job. It applies to composite objects, independent prop sets, and vegetation, not the character/rig workflow.

You are working inside AetherFlow. Read `ui_get_context` and `asset_job_get` before changing state. Resolve the current job, selected item, main stage, language, original artwork, accepted inputs, pending candidates, and current versions. If a request names a plan, read `plan_get_context` and use `plan_start` rather than creating duplicate jobs. Keep one working directory and bound Codex session per job; selecting another item is a context change, not a new session.

For a building that can be modularized, propose reusable continuous wall masters, separate windows, independent beams and framing, independent doors and roof pieces rather than one whole-building shell. Repeated matching parts are instances of a single master. Do not create separate wall variants merely to include window or door openings: windows and doors are separate objects, and the user removes the corresponding wall geometry and installs them manually. Different wall materials, textures or real construction may warrant a separate continuous wall master. Existing approved work is preserved; propose any changes for human review. Use `references/composition.md`, `references/image-generation.md`, and `references/assembly-and-export.md` for boundaries and downstream handling. This is a principle for suitable buildings, not a fixed house-only parts list.

For composite buildings, follow the source-counted complete-envelope policy in `references/composition.md` from the initial composition proposal through assembly requests and corrections. Inspect the registered artwork and crop before placements; count habitable storeys separately from attic/gables; infer unseen sides consistently and record their assumptions and `placementConfidence: inferred` evidence; reuse accepted masters across floors using their actual bounds and local axes. Inspect the assembled building visually from all required sides before offering its scene candidate, and report any unavailable view as unverified. Explicit user exclusions and open/cutaway designs take precedence. This policy does not turn prop-sets, trees, foliage or independent props into buildings.

Catalog every wall, wall variant and standalone window with both `front` and `side` views, so the job has separate slots for both. For roofs, process only the views in the accepted catalog; a side is required only when that catalog lists it. When a listed roof side is needed, preserve the silhouette, pitch and thickness in that separate view. If an existing approved wall/window catalog omitted a required side, use the supported catalog update and human review while retaining the same master ID, front image, candidate history, instances and unrelated accepted results. With AI depth enabled, modules get matching depth roles for every required view; each shared prop gets only `depth:front`, even when its color catalog also includes a side. Do not add sides indiscriminately to unrelated props; foliage keeps its separate four-view workflow.

## Non-negotiable rules

1. SQLite-managed records and artifact hashes are authoritative. Use registered artifacts and the job's canonical `work/assets/<jobId>` paths. Obtain actual paths from the application; never guess a workspace path or return the raw content-addressed object path as a user handoff.
2. Treat the original color artwork as the design source. Preserve intended materials, ornament, proportions, and palette. Remove reference-only motion, wind, perspective, and lighting artifacts without inventing a different design. A crop is an aid, not a replacement for the original.
3. Use the five main stages in this order: Reference, Composition, Images, Geometry, Assembly. Geometry includes individual model returns, segmented shared props, shared texturing, local foliage cards, and optional reference inspection. Older `asset-1` records with the former `materials` stage or a job stage of `materials` are read as Geometry; accepted item IDs, slots, candidates, files, history and revisions remain intact. Do not ask for re-acceptance just because navigation was normalized. Navigate to the actual job/item/stage through MCP and keep the user's selected files visible.
4. Use manual Tripo handoffs. Prepare a normal readable folder, explain its contents and the manual operation, then wait for returned files. Do not automate the Tripo website or call a paid generation API.
5. Compare usable attempts privately and submit only the single best matching image per job/item/role as the visible candidate, with quality warnings if needed. Never claim it is in a slot after registration alone. Read the slot back. Human review is separate from successful generation, and MCP must not silently accept results. Preserve existing candidate history without deleting or automatically accepting it.
6. Make corrections as new versions, with checkpoints before destructive work. Accepted source files are immutable. An accepted current version must feed subsequent steps, instances, assembly, and exports; an unreviewed candidate must not replace it.
7. Use deterministic, validated operations for sheets, crops, segmentation, surface splitting, foliage cards, assembly, and export. Inspect the tool schema and script help instead of inventing flags. Inspect evidence and conservation checks, not just exit codes.
8. User-facing instructions, copied prompts, and replies use the app language. This skill and technical references remain English. Explain a blocker with the affected item, what has been preserved, and one concrete recovery action.

## Work through the whole catalog

When the user starts the image stage for the entire list, treat it as one job-wide request. Build an explicit, human- and model-readable TODO from every accepted master in catalog order, with the master name and actual item ID, every required color role, and its saved status (`TODO`, `ACCEPTED_CURRENT`, `ACCEPTED_STALE`, `ACCEPTED_FRESHNESS_UNKNOWN`, `PENDING_CHECK(n)`, or a specific blocker). Use the accepted catalog as the source of roles: walls and windows require front and side; roofs get a side only when listed; foliage uses front, back, side, top. Work one master at a time and finish its actionable roles in front-then-side order (foliage in its listed four-view order) before moving to the next master. Inspect actual pending candidates before skipping; preserve accepted data and suitable pending candidates. After each submission, read back the slot, refresh the TODO from saved state, and continue immediately with the next actionable role. Do not finish a normal run after one image while another independent color role remains actionable, and do not wait for human acceptance before generating other independent colors. Generate missing or stale required outputs in this same request instead of asking the user to restart for each item or view. Keep the original artwork and candidate history. For each item/role compare attempts and submit only one best result to the matching slot. A genuinely blocked role gets its exact reason recorded while other actionable roles continue. Derived outputs wait only for their actual accepted-input dependencies: module depth views wait for their matching accepted colors; shared props use only `depth:front` when enabled; the geometry sheet uses each prop’s accepted depth front when enabled or accepted color front otherwise; foliage atlas/cards wait for all four current accepted foliage views. Never generate `depth:sheet`. Generated candidates remain pending for human review; only the user accepts them. A resumed request rebuilds the TODO from durable saved role state, skips valid candidates, and starts with the first unresolved role. If interrupted or partially successful, list remaining items and actual blockers; never claim the list is complete.

Execute the requested batch now in the current session, using the image-generation tool available there. A prepared prompt, table or plan is not a generated result. Generate and submit every independent color view that can be processed now without waiting for human acceptance; only derived outputs with actual accepted-input requirements must wait. After each submission, verify the matching slot. If a tool or required input is unavailable, report the exact unfinished roles and the actual blocker; do not imply that images were created or uploaded.

Apply the same visual inspection and source-anchored retry discipline as the character-view workflow. For each standard item, create the strict orthographic views listed by the accepted catalog, in front-then-side order; walls and windows require both, while roofs and other items receive a side only when listed in the catalog. Open each actual result before submission; verify one object and one requested view, angle, framing and fidelity to the original. A 3/4 view, multi-view collage or wrong profile fails the requested role: correct the prompt and regenerate from the original rather than submitting it as good. Continue independent roles and keep previous data; identify any genuine blocker. Four separate foliage views and explicitly composed shared-prop sheets are distinct exceptions. Application file validation alone does not establish visual correctness.

Do not treat uncertain or imperfect source fidelity as an automatic reason to hide all work. Privately compare usable single-view drafts and submit the single best version to its exact pending slot with concrete visual warnings; do not submit every intermediate attempt. Small, hidden or indistinct features may be approximate and must be described as such instead of guessed or demanded to match unseen detail perfectly. Retry for a concrete visible defect supported by the source, changing prompts or conditioning; stop retrying that defect if an attempted correction does not materially improve it, keep the best usable version and state the unresolved issue. Do not pursue uncertain hidden details or cosmetic polish indefinitely, and do not stop at an arbitrary attempt count while an actionable fix is still producing improvements. Only report a true blocker as a blocker, and never imply that a draft is accepted or the batch complete.

All alternatives and corrections preserve the original artwork's own style, brushwork, texture detail, palette and design. Do not switch to a cleaner, more polished or more realistic treatment as an automatic improvement. Multiple private attempts are allowed, and each must follow the same original style; select and present just the best matching candidate per role. Keep original source artwork primary for each attempt and record actual differences honestly.

For an oversized catalog, follow the request's `asset_job_get` pagination for both masters and shared sources. Collect all pages, preserving the actual owner, item IDs, roles, sheet mappings and job/workflow revisions. If either revision changes, restart the read instead of combining different versions. The full job specification comes from the first master page; later pages carry compact metadata. A paged request still means one request to process the entire catalog, not a sample or a request for the user to split it. If a page or the advertised paging operation is unavailable, report that actual failure and leave the job intact.

Apply the same whole-job approach to eligible handoffs, returned file mapping, preparation and scene operations when an existing tool can process multiple items safely. Handle ambiguous assignments explicitly and keep Tripo generation manual. A user may still select an individual item for inspection or an intentional correction.

## MCP responsibilities

MCP tools can be deferred and absent from the initial list visible to the model. If `tool_search` exists, search for the exact name with `mcp__aetherflow` and then by purpose; inspect the discovered tool's actual schema. If the dedicated catalog tool is unavailable but `asset_job_update` is visible, use its published catalog-proposal operation: serialize the already prepared proposal into its bounded `catalogProposal` JSON string, supply the current job `expectedRevision` and separate `expectedWorkflowRevision` from `asset_job_get`, and do not mix this operation with ordinary update fields. The server validates it through the same catalog operation. Read back the pending proposal and request human review. If neither supported path is available, preserve the draft and distinguish server connectivity from model tool discovery; never claim submission or edit application data directly.

The catalog JSON accepts only `items`, optional `instances`, and optional `assumptions`. Each item has required `name` and `route` (`module`, `shared-prop`, or `foliage`), and may have `id`, `dimensions`, `views`, and `depthEnabled`. For modules, also set `viewType` to `wall` for wall variants, `window` for standalone windows, `roof` for roof parts or `other` for other modules; do not set it on foliage or shared props. Walls and windows require `["front","side"]`; tiled or pitched roofs also need both views. For other standard items use `["front"]`, adding `"side"` where a separate profile is needed. Foliage uses the four separate front, back, side and top views. Give a new item a UUID if an instance refers to it. Each instance has `masterItemId` and `transform` with `position`, `rotation`, and `scale` arrays of three numbers; `id` is optional. `placementConfidence` may be `source-supported`, `inferred`, or `uncertain`, with a concise `placementEvidence` note. Dimensions and scale must be positive; position and rotation must be finite. Omitted `instances` preserve current placements. A composite catalog may be accepted before placements are ready, but an empty active list always blocks stage-5 validation, scene building, and export. Once accepted models are available, prepare an explicit placement repair; repeated parts reuse a master ID but each occurrence has its own instance ID and evidence-based transform. Do not use shared identity transforms as a placeholder. For example, serialize `{"items":[{"id":"00000000-0000-4000-8000-000000000001","name":"Wall","route":"module","viewType":"wall","views":["front","side"]}],"instances":[{"masterItemId":"00000000-0000-4000-8000-000000000001","transform":{"position":[0,0,0],"rotation":[0,0,0],"scale":[1,1,1]},"placementConfidence":"inferred","placementEvidence":"Example only; replace with evidence from this job."}],"assumptions":[]}` as the `catalogProposal` string. Job ID and both revision numbers belong to the outer tool call, not the JSON string. Use real unique IDs and transforms derived from the actual source and models for an actual proposal; never copy sample values.

- Create and inspect work using `asset_job_create`, `asset_job_list`, `asset_job_get`, and `asset_job_update`.
- Submit the catalog with `asset_job_catalog_submit`; submit generated or returned candidates with `asset_job_submit_outputs`.
- Inspect segmented surfaces with paginated `asset_job_components_list`. Use `asset_job_surface_run` for the registered deterministic operation, including grouping, controlled face splitting, foliage building, and assembly.
- Use `asset_job_handoff_prepare` with `kind: "texture"` only for shared props partitioned from the current accepted shared model and accepted in their own slots. Module models already contain their Tripo textures; keep them with their accepted model dependencies and omit them from texture handoffs, waiting lists, and completion counts. Use `asset_job_validate` before `asset_job_export`. For composites, read `asset_job_get` immediately before each assemble or export and supply its current `workflow.revision` as `expectedRevision`; use `asset_job_surface_run` with `mode: "assemble"`, inspect its pending scene in the UI, and wait for an explicit human acceptance before export. A selected current pending scene remains a valid target for whole-scene inspection and placement correction; never accept or reject it automatically. Prop-sets validate and export independent models without building a scene.
- For external returns, use `asset_job_return_map` to inspect uniquely matched or ambiguous assignments, then `asset_job_return_submit` to validate and submit them. Never guess among multiple matching masters or bypass model preflight through a generic data write.
- For common prop models, inspect `asset_job_shared_sheets`, register each model with `asset_job_shared_import`, and propose the separation inputs with `asset_job_shared_submit`. Read the job's `sharedSources` back. Keep every input bound to its exact sheet, not an individual prop's geometry. In one requested run, process all eligible human-reviewed sources sequentially using each `sharedSourceId` with inventory, inspection and partition; keep their hashes and mappings separate. Use `itemId` only for the existing current-individual-model path. Do not provide both selectors or substitute a fabricated item ID.
- Use `asset_register` for job/item-owned files, `ui_navigate` to show them, and `model_workbench_*` for localized model/texture corrections. A model must belong to this asset job; never supply a fake character ID.
- Inspect available schemas first. A tool acknowledgement is not proof of visual correctness, human acceptance, or successful navigation. Read back actual state.

The checked surface modes cover `sheet`, `crop`, `normalize`, `inventory`, `inspect`, `partition`, `guide`, `foliage`, and `assemble`. Whole-job assembly has its own candidate and dependency snapshot; accepting an outdated scene is not a way to refresh it. Rebuild from current accepted masters and active, reviewed instances.

## Completion

Report which items are ready, which require human review or manual Tripo work, the actual handoff/export folder, and any failed check. Never describe a partial set as complete. Continue fixing ordinary quality failures from source-anchored inputs within the authorized task. If no safe useful next action exists, preserve candidates and give a precise recovery choice instead of silently leaving stale slots.


## Depth generation: shared character representation and encoding tolerance

For every requested depth pair, read `references/depth-generation.md` and attach `references/depth-style-example.png` together with the exact accepted paired color view. The example is the same representation used by the character workflow; it never replaces the actual asset geometry. Generate ONE view, not a four-panel sheet. Process the ordered TODO for all actionable module pairs front then side; for shared props, prepare only the front pair. Continue after local failures.

Do not reject near-black pixels (1,1,1) or (0,1,0), or tiny RGB differences: the application uses the same tolerant technical validator as Characters. Submit usable original files as pending candidates with truthful warnings; byte equality of channels is not the visual-depth objective. Depth is generated volume, not desaturation of the color reference. Never use a defect on two pairs as evidence that the remaining independent pairs cannot be generated.
